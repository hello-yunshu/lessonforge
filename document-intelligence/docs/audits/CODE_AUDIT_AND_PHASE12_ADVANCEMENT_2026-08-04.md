# Phase 11复审与Phase 12推进审计

## 审计基线

唯一基线为 `document-intelligence_phase11_1.0.2.zip`。Phase 12没有从其他工作目录
拼接源码，也没有将上一轮文字结论当作代码事实。

## 审计判断

Phase 11在协议冻结、不可变数据、Rill边界和资格编排上具备较强基础，但不能直接作为
发布版。原发布就绪审计确认的核心阻断包括：核心API缺少统一认证、项目许可缺失、
PyMuPDF与基础能力耦合、CI与Makefile阶段滞后、容器和依赖不可复现、能力状态容易被
误读为生产资格。

## 本轮关闭的阻断

| 阻断 | Phase 12处理 |
|---|---|
| 核心API未认证 | 生产档统一租户认证、资源授权、限流与审计 |
| 跨租户资源ID猜测 | 返回404并保留访问审计 |
| LICENSE/NOTICE缺失 | Apache-2.0许可证与NOTICE进入源码包和wheel |
| Native PDF依赖PyMuPDF | base改为pypdf；PyMuPDF下沉为可选渲染器 |
| 容器默认公网暴露 | Compose绑定127.0.0.1，生产配置启动硬门禁 |
| Docker基础镜像未固定 | 无digest参数即构建失败 |
| CI停在Phase 10 | 唯一流水线执行Phase 1—12 |
| Makefile指向旧打包器 | `make package`改为当前可复现构建器 |
| wheel不稳定 | 两次构建后归一化并比较SHA-256 |
| 缺少SBOM/密钥扫描 | 生成SPDX SBOM并执行源码密钥扫描 |
| 测试时长无预算 | 四批120秒上限，记录执行证据 |
| 缺少系统级恢复 | 添加工作区备份、完整性验证和空目录恢复 |
| 能力过度声明 | 新增受限能力矩阵和发布候选边界 |

## 仍然开放的发布条件

下列事项不能仅靠本轮代码自动制造，继续作为稳定版阻断：

- 托管CI中Ruff、Mypy、pip-audit与容器扫描全部成功；
- 真实多领域质量证据；
- 固定、签名且可追溯的外部解析器产物；
- 168小时Soak与规模恢复；
- 试运行和独立发布批准；
- 可选渲染器许可证明；
- 更高的错误分支覆盖率。

## 最终结论

Phase 12工程实现通过，可发布为**受限单节点自托管候选版** `1.0.3-rc.1`。无条件
生产稳定发布仍不通过。

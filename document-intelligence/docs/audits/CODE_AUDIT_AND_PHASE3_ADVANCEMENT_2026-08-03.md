# 0.2.0复审、Phase 3推进与自审

## 1. 审核方法

本轮没有直接在上一轮工作目录上继续修改，而是：

1. 从 `document-intelligence_phase2_0.2.0.zip` 独立解压；
2. 校验上一阶段审计、阶段计划、源码和测试结构；
3. 在独立目录运行上一版本测试；
4. 先修复复验中发现的可移植性缺陷；
5. 实施Phase 3；
6. 进行实现后反向审计；
7. 执行测试、覆盖率、Schema、wheel和独立解压门禁。

## 2. 对0.2.0的补充审核结论

0.2.0核心匹配能力可以作为Phase 3开发基线，但交付包中存在一项此前未识别的问题：

- CLI集成测试把 `DI_PARSER_CONFIG` 写死为原开发目录的绝对路径；
- ZIP在其他路径独立解压后，两项CLI测试失败；
- 运行代码本身已提供包内默认配置，但测试没有验证这一真实分发路径。

该问题不影响标准匹配算法，但证明上一轮“独立解压后全部测试通过”的结论缺少可移植环境隔离。0.3.0已将测试改为包内默认配置，并新增发布验证门禁，防止再次引入开发机绝对路径。

## 3. Phase 3新增能力

- 独立Structure Result协议和JSON Schema；
- 单栏、双栏和稀疏并排块的阅读顺序；
- 全宽锚点分段；
- 标题层级、父子关系和内容作用范围；
- 文本组、视觉—图注组和表格—图注组；
- 有证据的 `caption_of` 和 `continues_on` 关系；
- 重复页眉、页脚和页码过滤；
- 整文档结构指标和诊断；
- 来源绑定、不可变结构存储和篡改检测；
- API、CLI、Schema、Docker Compose和CI接入；
- Rill Observe 0.3结构信号，保持Shadow。

## 4. 实施后反向审计发现

| 级别 | 发现 | 风险 | 修复 |
|---|---|---|---|
| P0 | 结构结果初版读取时只验证自身文件，没有反查来源解析运行 | 来源丢失后仍可能把派生结构当作可信事实 | `StructureService.get`强制重读来源运行并核对文档ID和语义摘要 |
| P1 | 跨页边界候选初版重新按几何坐标排序 | 多栏页面可能选择错误的页尾或页首元素 | 改为沿恢复后的正文阅读顺序取边界候选 |
| P1 | 无显式图注前缀时，普通短正文可能因紧邻图片被关联 | 产生无依据图文关系 | 增加紧密间距、居中、宽度收缩和长度联合门禁 |
| P1 | 少于4个元素时直接退回纵向排序 | 稀疏双栏或左右卡片顺序错误 | 增加强水平间隔和垂直重叠检测 |
| P1 | 引擎摘要只绑定算法文件 | 结果模型变化可能不触发引擎摘要变化 | 同时绑定engine.py和models.py |
| P1 | Phase 2测试使用旧绝对配置路径 | 分发包换目录后测试失败 | 删除绝对路径，使用wheel内默认配置并加验证项 |

## 5. 证据与安全边界

Phase 3坚持以下约束：

- 阅读顺序必须完整覆盖来源元素；
- 正文阅读顺序与被排除边缘元素必须严格分区；
- 关系、组和大纲节点必须引用证据；
- 关系不能引用来源文档中不存在的元素；
- 结构存储清单绑定结果SHA-256和语义摘要；
- 结构结果绑定来源解析运行和来源语义摘要；
- Rill不得写结构、修改阈值或执行生产动作。

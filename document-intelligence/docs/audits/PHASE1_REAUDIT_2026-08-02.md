# Phase 1 交付代码独立复审与修复报告

## 1. 复审方法

本次没有直接信任上一版实施报告，而是从交付 ZIP 独立解压后执行：

1. ZIP 完整性检查；
2. ZIP SHA-256 与旁路摘要比对；
3. 包内 `SHA256SUMS` 全量校验；
4. 源码编译和全部测试重跑；
5. Schema、存储、外部网关、API、打包和证据链逐文件审查；
6. 针对运行标识碰撞、路径标识、证据留存和失败隔离编写额外复现脚本。

原 ZIP 的摘要和包内文件哈希均正确，原有 24 项测试也全部通过。但测试通过不能替代架构与安全审查。

## 2. 原 0.1.0 冻结结论

**冻结不通过。**

0.1.0 可以作为修复基线，但上一版“工程实现通过、生产冻结有条件通过”的判断过于乐观。除外部解析器尚未资格测试之外，还存在会影响运行隔离、证据完整性和可复现性的内部问题。

## 3. 主要问题

### P0-1：运行标识没有绑定完整请求上下文

原 `NativePdfParser` 的 `parse_run_id` 只绑定：

- 输入内容 SHA-256；
- 解析器 ID 和版本；
- 部分静态配置。

它没有绑定文件名、Domain Pack 和请求选项，也没有绑定解析器实现摘要。实测同一文件内容使用不同文件名或 Domain Pack 会生成相同运行 ID，但语义输出摘要不同，随后在存储提交时触发冲突。

影响：

- 合法请求之间互相冲突；
- 实现升级但版本未变时可能复用旧运行身份；
- 无法可靠审计“同一次运行”究竟使用了什么上下文。

### P0-2：原始输入文件没有留存，证据链不完整

原系统只保存解析器的 JSON 原始输出，没有保存上传的 PDF 或图片。`SourceDescriptor` 只有文件名和哈希，没有可解析的 `source_ref`。

同时，原生 PDF 中的嵌入图片元素会生成 `asset_ref=sha256:...`，但图片字节没有写入资产库，形成悬空引用。

影响：

- 不能仅凭运行产物重放或核验解析；
- 无法从证据对象回到原始文件；
- 图片资产引用不可解析；
- 不满足“所有对象可追溯”的冻结要求。

### P0-3：外部结果中的标识符未限制为安全路径标识

`parse_run_id`、页面 ID、元素 ID 和证据 ID 原先只是普通字符串。文件存储直接把 `parse_run_id` 拼接到路径中。

包含 `/`、`..` 或绝对路径形式的标识会导致路径解析异常、读取越界风险或稳定拒绝服务。现有临时目录实现阻止了部分直接写出，但这不能视为安全边界。

### P0-4：文档图结构校验不完整

原 Schema 只检查页面引用的元素是否存在，没有检查：

- 页面列出的元素是否真的属于该页；
- 每个元素是否都出现在所属页面的 `element_ids` 中；
- Evidence 的 `parse_run_id` 是否和文档一致；
- Evidence 的页面引用是否存在；
- 重复关系 ID、重复页面序号等一致性。

这会允许形式合法但图结构错误的数据进入标准结果。

### P1-1：默认配置依赖当前工作目录

安装后的 CLI 或 API 从任意目录启动时，默认读取 `./configs/parsers.yaml`。普通 Python 包安装并不包含该目录，导致导入或启动失败。Docker 中恰好复制了配置，掩盖了此问题。

### P1-2：运行提交存在并发竞争和孤立原始输出

两个进程同时提交相同运行时，后提交者可能因目标目录已存在而被记录为失败。原始输出又在运行目录提交前单独写入，后续步骤失败时会留下孤立文件。

### P1-3：文件类型判断会信任扩展名

无法识别魔数时，原代码会根据文件名扩展名猜测 MIME。把任意内容重命名为 `.pdf` 即可进入 PDF 解析流程。

### P1-4：原生 PDF 缺少资源边界

原实现没有明确限制：

- PDF 页数；
- 单页块数量；
- 加密 PDF；
- 空 PDF；
- 异常页面尺寸。

小文件仍可能通过高度压缩结构产生过量资源消耗。

### P1-5：外部网关响应体无上限

外部解析服务返回的 JSON 会被整体读入内存，没有 `Content-Length` 和流式字节上限门禁。

### P1-6：生产依赖许可证门禁未登记

原交付将PyMuPDF作为核心Native PDF解析依赖，却没有在第三方依赖清单中登记其AGPL-3.0/Artifex商业许可证双重许可，也没有把许可证选择作为生产发行门禁。该问题不改变算法测试结果，但会直接影响闭源商业部署与发行方式。

修复后已：

- 将PyMuPDF加入运行时许可证清单；
- 明确标记为生产审查阻断项；
- 新增ADR要求PDF解析与渲染器保持可替换；
- 在README、运维文档和依赖报告中重复提示该边界。

### P2：工程质量遗漏

- `NativePdfParser._font_sizes` 重复使用两次 `@staticmethod`；
- macOS 的 `ru_maxrss` 单位与 Linux 不同，但字段统一标记为 KB；
- CLI 完全没有测试，整体覆盖率掩盖了 CLI 0% 覆盖；
- 同步解析直接运行在 FastAPI 异步端点中，会阻塞事件循环；
- 所有领域异常一律返回 422，没有区分 400、415、502、503、504。

## 4. 0.2.0 修复

以上问题已经在后续实现中修复：

- Schema 升级为 1.1；
- 所有文件系统标识使用安全 ID 约束；
- 新增 `request_context_digest`；
- 运行 ID 绑定请求上下文、解析器实现摘要和配置摘要；
- 原输入写入内容寻址 `sources/`；
- 嵌入图片写入内容寻址 `assets/`；
- 原始输出进入运行目录，与运行清单共同提交；
- 并发重复提交读取并核验既有结果，不再误记为失败；
- 强化页面、元素、关系和证据图一致性；
- 包内提供默认解析器配置；
- 文件类型只依据信号特征并使用 Pillow 校验图片；
- 增加 PDF 页数、块数、加密和空文档门禁；
- 外部响应采用流式大小限制；
- API 把同步工作移入线程池并区分错误状态；
- 增加 CLI、存储、碰撞、路径、证据和匹配回归测试。

## 5. 修复后判断

0.2.0 已消除本次复审发现的 P0/P1 阻断项，可以作为 Phase 2 的工程基线。

仍然保留的条件：

- PaddleOCR、OpenDoc、MinerU 仍未用固定生产镜像和真实模型完成资格测试；
- 当前匹配基准是小型合成回归集，不能声称生产准确率；
- Rill 仍只允许 Shadow 观察事件；
- 标准库写权限默认关闭；
- PyMuPDF许可证仍是生产发行门禁，必须选择AGPL兼容、商业许可或替换实现。

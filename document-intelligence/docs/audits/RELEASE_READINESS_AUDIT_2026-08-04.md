## 一、结论

### 1. 发布判断

| 发布类型 | 结论 |
|---|---|
| 无条件公开生产稳定版 | **NO-GO** |
| 处理敏感文档的公网服务 | **NO-GO** |
| 受限、单节点、内网工程预览 | **CONDITIONAL GO** |
| 下一轮自托管发布候选 | **可以争取** |

当前工程不是“代码质量差”，而是已经完成了较强的协议、不可变存储、Rill边界和资格编排，但尚未完成一个正式软件发行必须具备的四个闭环：

1. **安全闭环**：核心接口统一认证、租户隔离、限流和数据治理；
2. **法律闭环**：项目许可证、NOTICE以及PyMuPDF发行方式；
3. **供应链闭环**：锁定、可复现构建、SBOM、漏洞扫描、签名与provenance；
4. **质量闭环**：真实数据、固定解析器产物、168小时Soak和真实试运行。

因此，下一轮应定义为：

> **Phase 12：Release Candidate Hardening（发布候选收口）**

建议目标版本为 **`1.0.3-rc.1`**，定位为：

> **受限自托管、单节点、默认安全、能力状态透明的发布候选版。**

它可以成为可下载、可安装、可审计的候选发行；但只有真实资格活动最终产生 `qualified=true` 后，才可升级为生产稳定版。

## 四、详细问题清单

### P0-01 · 核心解析、结果读取与领域执行接口缺少统一认证和限流

**级别：P0**

**证据**
- src/document_intelligence/api/main.py:437-487 的 /v1/parse、/v1/runs/{run_id}、/v1/structure/recover、/v1/structures/{structure_id} 未要求令牌。
- src/document_intelligence/api/main.py:520-547 的 /v1/match 默认无需令牌。
- src/document_intelligence/api/main.py:654-682 的 /v1/domain/apply 与 /v1/domain-results/{id} 未要求令牌。
- deployments/compose/docker-compose.yml:6-7 将 8080 映射到宿主；Docker 内 Uvicorn 监听 0.0.0.0。
- 未发现全局速率限制、租户隔离或反向代理强制认证。

**影响**

网络暴露后可被未授权上传最大50 MiB文档、触发CPU/内存密集解析、枚举或读取解析结果，形成数据泄漏和拒绝服务风险。

**下一轮修复**

引入部署配置档。生产档必须在启动时校验全局认证、请求大小、并发、速率限制和反向代理信任；核心读写接口统一鉴权，文档与结果绑定租户/主体；OpenAPI文档生产默认关闭。

**验收标准**

未认证请求全部返回401/403；跨租户ID不可读取；上传、解析和查询均有并发/速率门禁；安全测试覆盖绕过、重放和ID枚举。

### P0-02 · 发行包缺少项目 LICENSE/NOTICE，Python包元数据也未声明许可证

**级别：P0**

**证据**
- 项目根目录无 LICENSE、NOTICE。
- pyproject.toml [project] 无 license 字段。
- 构建出的 wheel METADATA 仅有 Name/Version，未出现 License、License-Expression、Classifier 或 Project-URL。

**影响**

外部用户无法确定项目本身的复制、修改和分发权利；依赖通知也无法随发行包传递。

**下一轮修复**

明确项目发行策略，加入项目许可证、第三方NOTICE、版权信息、依赖许可证生成流程，并同步wheel元数据。

**验收标准**

源码ZIP、wheel、容器镜像均包含相同LICENSE/NOTICE；许可证扫描无未知或冲突项；法务/维护者签署发行结论。

### P0-03 · PyMuPDF生产发行许可证仍未解决

**验收标准**

存在可审计的许可证证明或替换提交；SBOM/NOTICE与实际二进制一致；生产资格报告不再出现该阻断码。

### P0-05 · 依赖、容器与构建未达到可复现发行要求

**级别：P0**

**证据**
- pyproject.toml 使用版本范围；无带哈希的生产锁文件。
- build-system 使用 setuptools>=75，构建后端无上限/摘要。
- Dockerfile 使用 python:3.11-slim 可变标签，并直接 pip install .。
- 两次从同一源码构建wheel，SHA-256分别为 e0a6cf... 和 30c09b...；解压内容相同但容器字节不同。

**影响**

无法证明发布资产可从同一提交重复生成；依赖漂移会改变行为、漏洞面和许可证集合。

**下一轮修复**

生成带哈希锁文件；固定构建工具、Python基础镜像摘要和系统包；使用SOURCE_DATE_EPOCH/规范ZIP时间；双构建逐字节比较。

**验收标准**

干净环境两次构建的wheel、源码ZIP和容器镜像摘要一致；依赖锁与SBOM一致；构建不访问未声明依赖。

### P0-06 · 正式CI与发布入口落后于Phase 11，且缺少签名供应链

**级别：P0**

**证据**
- Makefile report/package 只运行到Phase 10，package指向 scripts/package_phase10_release.sh。
- .github/workflows/ci.yml 只执行 run/verify_phase1..phase10，遗漏Phase 11。
- 无正式release job、SBOM、漏洞扫描、容器扫描、SLSA/provenance、资产签名和发布回滚演练。
- GitHub Actions使用可变major标签而非提交SHA。

**影响**

本地审计通过不能保证GitHub发布资产包含最新阶段能力；供应链篡改与错误资产发布无法被独立验证。

**下一轮修复**

建立唯一release脚本/工作流，自动发现或显式运行全部阶段；固定Actions提交SHA；生成SBOM、扫描、签名、provenance和不可变Release。

**验收标准**

同一提交CI全部绿；Phase 11/下一阶段门禁真实执行；发布资产、镜像、SBOM和provenance均有可验证签名。

### P0-07 · 产品能力声明与真实解析器资格仍需严格收窄

**级别：P0**

**证据**
- Native PDF文本路线可运行；PaddleOCR、OpenDoc、MinerU仍为可选/默认禁用且未完成真实固定产物资格。
- 扫描件在无外部OCR时只能明确降级，不能视为生产OCR支持。
- DVC/MLflow当前为证明和血缘接口，不代表已部署真实服务。

**影响**

若发布说明宣称“多领域高精度文档解析平台”，用户可能误解扫描OCR、复杂结构和持续学习已达到生产质量。

**下一轮修复**

发布矩阵逐项标注 stable/preview/disabled/qualified；未资格能力默认禁用且UI/API明确返回资格状态。

**验收标准**

发布说明与运行时health/capabilities一致；任何未资格解析器不能被生产档启用；扫描文档支持声明与实测一致。

### P1-01 · 缺少生产级可观测性、就绪探针和告警体系

**级别：P1**

**证据**
- 源码中未发现结构化logging、Prometheus/OpenTelemetry或/metrics。
- /healthz只返回静态配置和简单状态，没有区分liveness/readiness，也不验证存储、解析器和Runtime依赖。

**影响**

无法定位请求、监测延迟/错误/队列/资源、判断实例是否可接流量或建立SLO。

**下一轮修复**

加入结构化日志、request/trace/document/run关联ID、指标、liveness/readiness、依赖健康、审计主体和告警建议。

**验收标准**

在故障注入下readiness正确下线；日志无敏感正文；核心延迟、错误率、队列、存储和Rill状态可监控。

### P1-02 · 数据治理不足：无完整保留、删除、加密和访问审计

**级别：P1**

**证据**
- 原文档与结果按内容寻址长期保存，但无统一TTL、删除/匿名化和法律保留策略。
- 未提供租户级加密密钥、静态加密集成或读取审计。
- 各管理域使用共享静态摘要令牌，缺少角色、轮换和主体身份。

**影响**

处理合同、试卷、教育资料等敏感文档时难以满足最小化、删除请求和访问追责。

**下一轮修复**

引入主体/租户模型、RBAC、令牌轮换、保留策略、删除墓碑、备份同步删除和KMS接口。

**验收标准**

跨租户隔离测试通过；删除/过期可审计；备份恢复不复活已删除数据；敏感字段不进入普通日志。

### P1-03 · 当前存储与并发模型应明确限定为单节点

**级别：P1**

**证据**
- 主要状态使用本地文件系统、O_EXCL锁和原子重命名。
- Compose只部署一个API服务；无分布式队列、数据库事务或对象存储一致性层。
- Phase 11 Bundle不是完整工作区备份/迁移工具。

**影响**

多副本部署、共享存储、故障转移和大规模并发下的语义未经证明。

**下一轮修复**

下一发布明确“单节点自托管”；加入完整工作区备份/恢复、迁移和灾难恢复演练。多节点能力另立阶段。

**验收标准**

发布文档明确拓扑；单节点恢复RPO/RTO有实测；不支持的多副本配置启动即拒绝或明显告警。

### P1-04 · 覆盖率门禁过于依赖综合百分比，关键分支覆盖不足

**级别：P1**

**证据**
- docs/phase-11/coverage.json 综合覆盖80.208%，但纯分支覆盖仅63.693%。
- cli.py 62.67%、structure/store.py 64.14%、production/service.py 66.25%、api/main.py 72.09%、matching/library.py 72.5%。

**影响**

**下一轮修复**

为安全关键模块设分支覆盖阈值；增加并发、短写、损坏、权限绕过、超时和恢复测试。

**验收标准**

总体分支覆盖达到约75%及以上，安全关键模块分支覆盖至少80%，任何豁免有书面风险接受。

### P1-05 · 测试超时和总时长没有正式治理

**级别：P1**

**证据**
- 单进程完整pytest未在当前审计执行窗口内完成。
- 重新逐文件执行55个测试文件均通过，无单文件超过45秒；累计进程耗时约262秒，最慢文件11秒。
- 项目未配置pytest-timeout、慢测标记、持续时长预算或duration基线。

**影响**

CI可能因锁等待、资源泄漏或慢回归无限拖延；无法区分工具总时限与真实挂死。

**下一轮修复**

加入单测/集成测试超时、--durations、慢测分类、并行策略和总时间预算。

**验收标准**

任一测试超时会明确失败；冷启动CI在预算内完成；连续多次运行无时间显著漂移。

### P1-06 · 生产代码使用assert承载运行时不变量

**级别：P1**

**证据**

**验收标准**

### P1-07 · 容器构建与运行硬化不完整

**级别：P1**

**验收标准**

构建上下文清单可审计；容器扫描通过；资源超限可控；生产Compose不直接公开未认证API。

维护者可能调用错误入口或引用过期指标。

**下一轮修复**

保留历史只读归档，新增唯一release入口和current状态文件；历史快照显著标记版本与生成时间。

**验收标准**

默认命令只指向当前阶段；过期状态不会被health、文档首页或发行脚本当作当前结论。

1. JSON结构化日志与关联ID；

1. 租户和主体级权限；
2. 保留、到期、删除、法律保留和删除墓碑；
3. 备份同步删除与恢复防复活；
4. KMS/静态加密接口；
5. 读取与导出审计；

### Workstream G：测试与质量门禁

6. 至少7天、500份真实文档的受控试运行；
7. 人工签署综合资格报告。
